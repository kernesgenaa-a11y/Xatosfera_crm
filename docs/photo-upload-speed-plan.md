# Аналіз швидкості завантаження фото та план оптимізації

Дата: 2026-04-01

## Що зараз уповільнює завантаження

1. **Послідовний пайплайн в UI для кожного файлу**
   - На сторінці редагування обʼєкта фото обробляються і відправляються **по одному** у циклі `for`.
   - Для кожного зображення виконується watermark + AVIF кодування на main thread, після чого лише тоді виконується `fetch` upload.
   - Це дає ефект “N \* (encode + upload)” замість конвеєра/паралелізації.

2. **Водяний знак для кожного файлу через повторний `fetch(watermarkUrl)`**
   - У `addWatermarkToImage` лого щоразу підтягується заново.
   - Це зайві декодування/мережа/CPU та затримка перед upload.

3. **Без адаптивного ресайзу перед AVIF**
   - Навіть великі оригінали (наприклад 4000px+) кодуються в повний розмір.
   - Це різко збільшує час кодування на клієнті та розмір файлу для передачі.

4. **Один endpoint upload без батчів/резюмування**
   - Бекенд приймає 1 файл на запит, ліміт 10MB.
   - Немає масового завантаження (batch), немає chunked/resumable сценарію.

5. **GET фото без edge-friendly кеш-стратегії**
   - Віддача файлів має `Cache-Control: private, max-age=3600`.
   - Для галерей/карток це зменшує повторне використання кешу між сесіями/користувачами (навіть якщо ключ файлу immutable).

6. **Завантаження фото в UI через `authFetch -> blob -> objectURL`**
   - `useAuthImage` кожного разу робить авторизований fetch і blob-конвертацію.
   - Це добре для захисту, але дорого для списків із багатьма картками (додатковий JS/heap/GC).

## Швидкі покращення (1-2 дні, найбільший ROI)

1. **Паралельне завантаження з обмеженням concurrency (3-4)**
   - Замість повної послідовності: робити пул промісів.
   - Очікуване прискорення відчутного TTI upload блоку: ~2-3x при 10-20 фото.

2. **Кешувати watermark bitmap один раз на сесію**
   - Завантажити і декодувати лого 1 раз, передавати в функцію обробки.
   - Зменшення накладних витрат на кожне фото.

3. **Client-side resize перед AVIF**
   - Наприклад обмежити longest side до 1920/2560 px для галереї.
   - Це зазвичай дає 40-80% зменшення ваги і суттєво зменшує час upload.

4. **Прогрес-бар на рівні batch + per file**
   - Навіть якщо абсолютна швидкість та сама, UX відчувається значно швидшим.

## Середньострокові покращення (3-7 днів)

1. **Винести обробку зображень у Web Worker + OffscreenCanvas**
   - Кодування AVIF/водяний знак не блокуватиме main thread.
   - UI лишається чуйним навіть при великій кількості фото.

2. **Додавання endpoint `/api/files/upload/batch`**
   - Приймати кілька файлів за один запит (або multipart mixed).
   - Менше HTTP overhead/handshake, простіше трекати прогрес.

3. **Перехід на presigned direct upload у R2**
   - Поточний воркер може видавати short-lived signed URL.
   - Клієнт шле напряму в R2, воркер не стає “вузьким місцем” для трафіку.

## Довгостроково (оптимальний прод-профіль)

1. **Асинхронний image pipeline на сервері**
   - Завантаження оригіналу -> queue -> генерація derivative-версій (`thumb`, `card`, `detail`, `full`).
   - Клієнт одразу працює з легкими дериватами, а full-res підвантажується за потреби.

2. **Immutable media keys + aggressive cache**
   - Ключ вже унікальний (`generateId` в імені), тож можна віддавати
     `Cache-Control: public, max-age=31536000, immutable` для фото.
   - Це радикально прискорить повторні відкриття сторінок.

3. **Responsive images (`srcset/sizes`)**
   - На картках вантажити thumb, в модалці detail/full.
   - Менше байтів, швидший рендер галереї.

## Конкретний технічний план змін у цьому репо

### Етап 1 (рекомендую зробити першим)

- `src/pages/PropertyEditPage.tsx`
  - Замінити послідовний `for` на `uploadWithConcurrency(files, limit=3)`.
  - Показувати прогрес (`processed/total`, `success/failed`).

- `src/lib/image-watermark.ts`
  - Додати memoized loader для watermark bitmap.
  - Додати resize (max dimension) перед накладанням watermark/AVIF.

### Етап 2

- `worker/src/files.ts`
  - Для image/\* віддати довший кеш (immutable), для документів залишити поточний policy.
  - (Опційно) додати endpoint batch upload.

- `src/hooks/useAuthImage.ts`
  - Додати in-memory LRU cache `key -> objectURL` + TTL.
  - У списках карток використовувати стабільний thumbnail URL (коли зʼявляться деривативи).

### Етап 3

- Додати воркер-чергу/джобу для дериватів та (опційно) presigned direct upload flow.

## Що міряти, щоб підтвердити прискорення

1. **Client metrics**
   - `time_to_first_uploaded_photo`
   - `time_to_upload_10_photos`
   - `main_thread_blocking_time` під час upload

2. **Network metrics**
   - Середній розмір фото після обробки
   - Throughput upload (MB/s)

3. **UX metrics**
   - Time to render first gallery thumbnail
   - P95 час відкриття модалки з фото

## Очікуваний результат після Етапу 1

- Upload 10-20 фото: відчутно швидше (орієнтовно 2x+) за рахунок паралельності.
- Менше “фризів” інтерфейсу під час масового завантаження.
- Менші файли після resize -> менше очікування у мобільних мережах.
